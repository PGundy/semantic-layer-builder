# Phase card: metrics

Load this card when `sl next` names phase `metrics`. It holds ratios and combined figures, and figures that span sources. Load `references/spec.md` (metrics.yaml) with it.

**Checklist:** 1. Write each metric in `metrics.yaml` as a draft. 2. Read back its formula in words. 3. `sl reply` with the answer; `sl approve --target metric:<name>` on a recorded yes.

Once the underlying measures are approved, ask which ratios and combined figures the business reports (average order value, conversion rate, net revenue), starting from the baseline's suggested ratios and shares. Before proposing one, check that every measure it combines can express the shared rules on every hop (refunds dropping test accounts through `order.customer`). Write them in `metrics.yaml` as `ratio` or `derived` per `spec.md`, each with a `description`, `format` and the measures it uses (a new metric is a write without a typed command: `SKILL.md`, Hand edits; `sl set metric:<name> <key> <value>`, `sl tag` and `sl rename metric:<name> <new_name>` change one that exists). A metric that combines measures of several models groups by dimensions every model it uses reaches through one path of to-one joins (refunds reach `orders.order_date` through their `order` join), or that exist with the same name in each: give a model with no such path a dimension of that name (a join reference such as `expr: order.created_at` dates refunds by their order's month) and approve it. Read back the formula in words ("revenue divided by number of orders, both excluding cancelled orders. Approve?"), record the answer with `sl reply`, and on a yes run `sl approve --target metric:<name>`. An approved metric may use approved measures only.

## Across sources

- Joins exist only within one source. When the owner asks a question that spans sources ("revenue by marketing campaign" with orders in the warehouse and campaigns in the lake), or a rule must cross sources (warehouse test accounts applied to lake sessions), record it as an open question on the relevant models and in the handoff, with the exact definition and any figure; do not model it in either source. If the owner wants it modelled, the route is a separate federating source whose engine already holds both sides, which the owner's engineers set up (Parquet copies of both, read by one DuckDB source's views, for example); a DuckDB source's setup cannot `ATTACH` another database.
- A metric spanning two sources (customer acquisition cost = lake spend / warehouse new customers) is two measures, one per source, each approved with its own golden. Record the formula, and any figure the owner gave, in both measures' descriptions and in the handoff, even when the owner keeps the metric in their own reports; do not write a metric. When one side cannot exist yet, record the formula on the measure that exists and an open question on the other model naming the missing column or view, or, when that model does not exist yet, on the existing measure's model and among the handoff's cross-source questions. A formula the owner never stated is an open question, not a description.
